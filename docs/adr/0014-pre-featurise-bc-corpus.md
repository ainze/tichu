# ADR-0014: Pre-featurise the BC corpus to a memmap bundle alongside replay-on-the-fly

- **Status:** Accepted
- **Date:** 2026-05-29
- **Related:** [ADR-0011](0011-bc-training-replay-on-the-fly.md), [ADR-0009](0009-bsw-ingest-streaming-pipeline.md), [ADR-0013](0013-parquet-schema-versioned-by-directory.md)

## Context

[ADR-0011](0011-bc-training-replay-on-the-fly.md) selected option α.2 —
archive-driven, parquet-as-manifest, replay-on-the-fly — and explicitly
rejected option β (cache serialised PrivateState in parquet) and γ
(cache dense Feature Vectors). The reasoning was correct at the time:
α.2 ships nothing new on disk, keeps versioning surface minimal, and
"plausibly faster than the featurizer it feeds" given how short Tichu
rounds are.

The 2026-05-29 pipeline-perf profile
([docs/notes/2026-05-29-pipeline-perf-fix.md](../notes/2026-05-29-pipeline-perf-fix.md))
overturned the "plausibly faster" assumption. With 10 worker processes
on a 12-core box running `ParallelParquetBCDataset`:

- **Worker py-spy flamegraph:** `replay_round` → `engine.step` →
  `legal_actions` consumes ~75% of every worker CPU-second. `featurize`
  is ~2.5%. IPC put-path (pickle + named-pipe write) is ~10%.
- **Main consumer flamegraph:** ~80% off-CPU, blocked on the queue.
  The pipeline is **producer-bound on engine replay**.
- **End-to-end throughput:** ~6,500 ex/s on the 100k smoke corpus —
  the upper bound a replay-bound pipeline can deliver without
  eliminating `replay_round`.

ADR-0011's rationale #5 ("Tichu rounds are short … microseconds-per-
decision in absolute terms … per-epoch corpus-scale replay is plausibly
faster than the featurizer it feeds") was the load-bearing claim. The
flamegraph shows that claim is **inverted in practice**: `replay_round`
is ~30× more expensive than `featurize`. The cost dominator is engine
state derivation, not feature math.

Two spike measurements quantify the prize:

- **Phase A — in-RAM ceiling.** Pre-load N BCExamples into RAM, run the
  BC training loop over the cache.

  | Arch | Params | Ceiling ex/s | vs current 6,570 |
  | --- | ---: | ---: | ---: |
  | Current full BC (1024×4, head 256, B=1024) | 26.9 M | **44,458** | 6.8× |
  | Wider BC (2048×6, head 512, B=1024) | 87.4 M | **18,018** | 2.7× |

- **Phase B — disk-backed delivered.** Materialise 250k examples to
  per-decision-type numpy memmaps (~17 GB), read them back through the
  same BC consumer.

  | Arch | Phase A ceiling | Phase B delivered | % of ceiling |
  | --- | ---: | ---: | ---: |
  | Current full BC | 44,458 | **19,059** | 42.9% |
  | Wider BC | 18,018 | **14,083** | 78.2% |

The gap between ceiling and delivered is per-row `BCExample` object
construction in the memmap reader (Python overhead, not disk IO; NVMe
sustained ~1.26 GB/s, well below spec). The
`MemmapBCDataset.iter_batches` path in
[`src/tichu_training/bc/materialised.py`](../../src/tichu_training/bc/materialised.py)
bypasses per-row object construction with a single fancy-index memmap
copy per batch — projected throughput ~35-40k ex/s for current, ~17k
for wider.

The original β rejection in ADR-0011 cited storage cost ("~5-20 GB at
100k, ~120-500 GB at corpus scale") and the coupling to engine-internal
PrivateState serialisation. ADR-0011's γ rejection cited ~13 TB at
corpus scale and the same coupling to FEATURIZER_VERSION.

The bundle proposed here is neither β nor γ exactly. It is **γ
restricted to a per-decision-type split** with the legal_mask written
as raw uint8 (not bit-packed) for zero-copy memmap views. Sizing:

| Corpus | On-disk size |
| --- | ---: |
| 250k example pilot (measured) | ~17 GB |
| 100k subset (~62 M decisions, extrapolated) | ~4.1 TB |
| Full 2.4M corpus (~1.5 B decisions, extrapolated) | ~100 TB |

A quantised layout (int8 features + bit-packed mask) reduces this ~4×
to ~1 TB for the 100k subset — within a single consumer 4 TB NVMe — but
quantisation is out of scope for this ADR.

## Decision

**Adopt option β' — pre-featurise to a per-type numpy memmap bundle —
as an additive training source alongside ADR-0011's α.2 replay-on-the-fly
path.**

α.2 remains the canonical pipeline. β' is the production path when the
training workload's wall-clock matters (wider-BC, future AWR-refine,
hyperparameter sweeps). The bundle is regenerated by an explicit one-shot
CLI pass; nothing in the runtime training loop produces it.

Concrete shape, all already shipped on this branch:

1. **Bundle layout.** Per-decision-type (`play` / `wish` /
   `dragon_assignment`) files, each as raw numpy `tofile()`:
   `<type>_features.dat` (float32 `(N, D_feat)`),
   `<type>_legal_mask.dat` (uint8 `(N, K_head)`, not bit-packed),
   `<type>_meta.dat` (structured `(target u2, sample_weight f4,
   skill_decile u1, round_outcome f4, game_won i1)`). Plus
   `order.dat` (uint32 `(N_total, 2)`, original emission order) and
   `manifest.json`.

2. **Triple version pin.** `manifest.json` records
   `featurizer_version`, `action_space_version`, and a new
   `schema_version` (the bundle's own layout/dtype contract; bumped
   independently of the featurizer's content version per the
   precedent in [ADR-0013](0013-parquet-schema-versioned-by-directory.md)).
   `MemmapBCDataset.__init__` refuses to load on any mismatch and
   raises `VersionMismatchError` from
   [`tichu_training.checkpoint`](../../src/tichu_training/checkpoint.py).
   Same error class as `Checkpoint` so existing handlers catch both.

3. **Writer:**
   [`tichu_training.bc.materialised.materialise(stream, out_dir,
   max_examples)`](../../src/tichu_training/bc/materialised.py).
   Drives any `Iterable[BCExample]` (typically
   `ParallelParquetBCDataset`) through the bucket-by-type + write-once
   pipeline. CLI wrapper:
   [`python -m tichu_training.cli.materialise_bc`](../../src/tichu_training/cli/materialise_bc.py).

4. **Reader:**
   [`tichu_training.bc.materialised.MemmapBCDataset`](../../src/tichu_training/bc/materialised.py).
   Implements `Iterable[BCExample]` for drop-in compatibility with
   `ParquetBCDataset` / `ParallelParquetBCDataset`. Adds
   `iter_batches(batch_size, *, drop_last=False, preserve_order=True)`
   which yields pre-stacked per-head batches — the fast path. Per-batch
   gather is a single vectorised memmap fancy-index copy.

5. **Bundle never becomes the source-of-truth.** The BSW archive and
   the parquet manifest remain canonical. The bundle is a cache: it can
   always be regenerated from the archive + parquet. Featurizer or
   action-space bumps invalidate it and require a re-materialise pass.

## Rationale

1. **The cost dominator measured by the 2026-05-29 profile is exactly
   the cost the bundle eliminates.** `replay_round` is ~75% of worker
   CPU; the bundle stores the post-replay BCExample stream, so
   training-time loads pay zero replay cost. The projected ~5× speedup
   for current BC and ~2.6× for wider BC matches the 2-10× range
   ADR-0011's β/γ rejection lines treated as "if wall-clock motivates
   it" headroom. Wall-clock now motivates it.

2. **The β/γ versioning concern is addressed by the schema_version
   pin.** ADR-0011 worried that β "commits the parquet to a serialised
   PrivateState format coupled to engine internals." That concern is
   real for β (engine-state-shaped on-disk format). It is **not real
   for β'** because the on-disk format is the BCExample contract — the
   same dataclass the trainer already consumes. Engine changes don't
   touch the bundle; featurizer changes do (and invalidate it via the
   pin). [ADR-0013](0013-parquet-schema-versioned-by-directory.md)
   established the precedent that schema-shape versioning belongs in a
   dedicated `schema_version`, separate from the content versions.

3. **The bundle is additive, not replacing.** ADR-0011 explicitly left
   β as an option ("β remains additive. If BC training needs many
   epochs and wall-clock dominates, backfilling the reserved
   `state` / `legal_actions_mask` columns in a one-shot pass is a
   non-breaking change"). β' is the same shape of move, with the
   on-disk format chosen to side-step the engine-internal-serialisation
   pitfall. `ParquetBCDataset` and `ParallelParquetBCDataset` remain;
   training configs that don't use the bundle are unaffected.

4. **Per-type split + raw mask is what makes the reader cheap.** The
   replay-on-the-fly path already keys batches by `decision_type`
   (per-head buffers in `train_one_epoch`). Storing per-type files lets
   `iter_batches` issue one fancy-index per batch with no cross-type
   merge, and a raw uint8 mask lets that index produce a usable boolean
   array via a single `astype(bool)` — no unpacking. The
   ceiling-delivered gap measured at the spike-script layer is closed
   by this reader path, projected from ~19k → ~35-40k ex/s for current.

5. **Storage cost is real but contained.** The pilot 250k bundle is
   17 GB. Extrapolated to the 100k subset that current BC training
   runs against, ~4 TB. A consumer 4 TB NVMe (~$300) covers it; the
   payback is one wider-BC run. Full corpus scale (~100 TB) is **not**
   in scope of this ADR — the production bundle stays subset-scale
   unless and until full-corpus runs become routine.

6. **Re-materialise is bounded.** The materialise pass runs at the same
   2,114 ex/s as the parallel parquet dataset minus per-row Python
   bookkeeping. ~50 min for the 100k subset, ~20 hours for the full
   2.4M corpus. A featurizer or action-space bump triggers one such
   pass per (corpus, version). One pass per quarter is the realistic
   cadence.

## Consequences

- **`ParquetBCDataset` and `ParallelParquetBCDataset` are unchanged.**
  Training configs that don't reference the bundle behave identically.
  The bundle is opt-in.

- **`train_bc` will gain a new dataset config option in a follow-up.**
  Today's CLI takes `dataset: parquet` or `dataset: synthetic`. A
  `dataset: memmap` option will point at a bundle directory and
  instantiate `MemmapBCDataset`. Out of scope for this ADR — the source
  module is shipped, the CLI wire-up is one line in `_build_dataset`.

- **`iter_batches` introduces a second yield contract for BC training
  data.** Existing code expects `Iterable[BCExample]`. The fast path
  yields `(decision_type, dict[str, np.ndarray])`. `train_one_epoch`
  will need a switch — or a thin adapter that consumes `iter_batches`
  output directly into `model(...)` calls bypassing `_to_tensors`. The
  adapter is bounded in scope; signed off as a follow-up.

- **Bundles are version-coupled.** A featurizer bump (per
  [ADR-0013](0013-parquet-schema-versioned-by-directory.md)'s
  `FEATURIZER_VERSION` semantics) invalidates every bundle on disk. The
  `VersionMismatchError` raised by the reader makes that failure mode
  loud at training-loop start, not silent at evaluation time. Operators
  must re-materialise after any such bump.

- **Disk is now a dependency of fast training.** Not a tax on smoke
  runs (which use `SyntheticBCDataset`) nor on the legacy path (which
  still works), but for the new wide / fast-iteration workflows the
  4 TB NVMe is a hard requirement. A run that points at a missing
  bundle gets a `FileNotFoundError` with a hint to run
  `python -m tichu_training.cli.materialise_bc`.

- **The bundle is not a transport format.** It's a local cache — paths
  inside the manifest aren't portable across machines. Copying a bundle
  between machines works (paths are relative) but the bundle is large
  enough that re-materialising from a shared archive is usually
  cheaper than copying.

- **The 100 TB full-corpus scenario remains rejected for now.** The
  decision here is for the smoke / 100k / wider-BC scale. If full
  corpus throughput ever matters, a follow-up ADR would have to look
  at quantisation (int8 features, bit-packed mask: ~4× reduction) or
  partial materialisation (high-skill rounds only).

## Rejected alternatives revisited from ADR-0011

- **γ. Dense feature memmap, no per-type split.** Still rejected.
  Without per-type split, every batch needs a merge step before the
  trainer's per-head loss; the gather is more expensive and the
  bit-mask becomes the bottleneck. The per-type variant chosen here is
  ~strictly easier for the consumer.

- **β. Cache serialised PrivateState in parquet.** Still rejected. β'
  stores the BCExample (post-featurise) not the PrivateState (pre-
  featurise), so it doesn't couple the cache to engine internals.
  Re-running the featurizer over cached state would still pay the
  ~2.5% featurize cost per training step — small, but pointless when
  the alternative is to cache once.

- **Continuing with α.2 only.** Rejected for the wider-BC and
  hyperparameter-sweep workloads. α.2 remains the canonical path for
  small smoke runs where the materialise overhead isn't justified.
